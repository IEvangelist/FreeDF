# Editor performance checkpoint: 2026-10-30

This is a bounded improvement, **not completion of the editor responsiveness
work**. Fresh rendering and some first-page opens still exceed the requested
latency goals. No fidelity reduction, thread enablement, AOT claim or live-site
deployment is part of this checkpoint.

## Measurement

Release, local static WASM, Playwright Chromium, 1440 x 1000, device scale 1,
Windows 11 / Core i9-10900 / .NET 10.0.14. Three fresh browser contexts per run,
four C#-generated samples (01, 03, 09, 20), plus a generated 12-page fixture
(report and six image pages). Every .NET/browser/benchmark command acquires the
shared validation slot independently; no coordinated workload runs alongside
a measurement window. OS/background activity is not controlled by that lock.

The matched control is the published-local artifact from `8adbee5`. The
candidate adds worker binary conversion/transfer and identity RGB/gray
conversion. Both matched runs use the same profiling script and regenerated
sample corpus. PNG SHA-256 values for the first page are identical before and
after, in all three repetitions of all five documents.

Timing includes the actual browser action, queued commands, paint waits and
any background work encountered by that action. It is not just .NET time.
The five-step overlay gesture and 12-step drag deliberately span multiple
animation frames: their total gesture duration is not a single-input response
time. Event-to-next-frame sampling in the extended harness measures that
separately; the under-100-ms response budget does not apply to a whole gesture.

Three observations per fixture are enough to detect these large repeatable
changes, not to characterize a production tail distribution: nearest-rank
p95 is simply the largest of the three. Do not rank narrow timing differences.
The [before CSV](2026-10-30-before.csv) and [matched after CSV](2026-10-30-after.csv)
retain all grouped measurements and budget outcomes, not just selected wins.

## Changes and memory

- Upload `File` objects are cloned to the PDF worker. Base64 conversion,
  command JSON construction and response base64 decoding happen there, not
  on the UI thread. Binary response buffers are transferred to the host,
  then wrapped in `Response` without a per-byte main-thread callback.
- PNG image transport deliberately remains immutable base64 data URLs with
  the existing 8 MiB JS cache. Cached image buffers are not transferred or
  detached; image decode/atomic swap/retry and render epochs are unchanged.
- Eight-bit DeviceRGB/DeviceGray images with identity Decode and no color-key
  mask copy bytes directly instead of doing dictionary lookup, floating-point
  color conversion and rounding for every pixel. Other color spaces, Decode
  transforms and color keys keep the general path. Soft/stencil masks and
  JPX alpha still run afterward.

This moves conversion allocations off the UI thread; it does not eliminate
the .NET JSON/base64 intermediate, the browser's response/blob copies, or the
large raster allocation. In a representative after-run, the large 240-dpi
operation allocates about 215 MB managed, with approximately 3441 ms raster
and 69 ms PNG encoding. Raw RGBA transport would not address that dominant
raster cost and would increase transfer size.

The worker remains single-threaded, without shared-memory isolation headers.
Browser `Parallel.For` guards stay intact. SIMD does not require COOP/COEP;
WASM threads do. The optional `wasm-tools` workload is absent, so these results
do not include AOT/publish optimization. Cold runtime/resource measurements
remain separate from steady-state operation timings.

## Regression coverage and gates

`ImageDecoderFastPathTests` compares fast and forced-general output across
all byte values, RGB/gray, truncated rows, soft masks, rendering intents and
black-point compensation. A separate case checks inverted Decode plus a
matching color key. Existing JPEG/JPX/ICC tests cover codec/mask interactions.
`EditorSessionTests` additionally compares cached overlay rendering with a
fresh render of the exported PDF, retaining the exact bare-page cache entry.

The browser profile writes raw JSON, `.summary.csv`, `.summary.json` and
`.budgets.json`. Budgets use strict less-than comparisons:

| Metric | p50 budget | p95 budget |
|---|---:|---:|
| Open / first editable page | 250 ms | 500 ms |
| Text-edit backend commit | 250 ms | 500 ms |
| Zoom/undo visual response | 100 ms | 200 ms |
| Cached zoom / page navigation | 100 ms | 200 ms |
| Event-to-next-frame maximum per action | 100 ms | 200 ms |
| Heartbeat / input acknowledgment maximum per action | 200 ms | 200 ms |
| Main-thread long task maximum per action | 50 ms | 50 ms |
| Sidebar active-page raster misses | at most 3 | at most 3 |
| Overlay-only bare-page raster misses | 0 | 0 |

The harness reports all latency misses after completing the run and fails by
default; it does not abort on the first miss and hide later measurements.
`EDITOR_PROFILE_REPORT_ONLY=1` is an explicit diagnostic mode, not a passing
performance result. Image continuity, pixel equivalence and rerender-count
assertions still fail immediately in that mode.

Both matched runs sampled over 5600 sidebar frames each across desktop/mobile
and five fixtures, with no unloaded/hidden/zero-size active image and zero
active-page raster misses. The dedicated `--page-image` smoke remains the
stronger nonblank-pixel, race and retry regression. Cache/dirty-region coverage
here means cached bare layer plus exact overlay/full-render equivalence; no
new dirty-rectangle renderer is claimed.

### Extended final run

The [controlled final CSV](2026-10-30-final.csv) adds the new cached,
event-to-frame and overlay-cache phases. Each document finishes on page 1 at
fit-page scale so the warm probes do not change the following fixture's
opening page or DPI. All 15 first-page PNG hashes match the control.
This extended workload is recorded separately from the original paired runs.

| Fixture | Cached zoom p50 / p95 | Cached page navigation p50 / p95 |
|---|---:|---:|
| Showcase | 58 / 72 ms | One-page fixture |
| Typography | 58 / 59 ms | 97 / 98 ms |
| Images | 58 / 59 ms | One-page fixture |
| Report | 60 / 60 ms | 97 / 97 ms |
| Large | 58 / 59 ms | 96 / 97 ms |

During drag, event-to-next-frame p95 is 16.0 to 16.4 ms across the five
fixtures. The entire sustained gesture still takes longer by design.
Overlay-only probes preserve the decoded bare-page pixel hash with zero
bare raster misses. Sidebar probes sample **2873 desktop + 2853 mobile
frames**, without a blank/hidden active page or an active-page reraster.

The [final budget misses](2026-10-30-final-budgets.json) contain **seven**
failing metric groups: startup long task (71 / 73 ms), showcase open
(714 / 848 ms), image open (391 / 434 ms), large open (452 / 465 ms), and
uncached typography/report/large navigation (181 / 183, 149 / 150,
149 / 149 ms). All pairs are p50 / p95. The final run is diagnostic
report-only, **not a passing latency gate**. Applying the same summary
budgets to the original control/candidate gives 14 / 7 misses; the default
summary command was explicitly checked to return nonzero for the failing
control, rather than silently accepting it.

No flaky wall-clock assertion was added to the unit suite. No speculative
fuzzer or unrestricted decoded-image cache was added: there was no new
malformed-input finding from this profile, and mutable resource/color-space
context makes an unconditional global image cache unsafe. Large-file limits
continue to use existing deterministic raster bounds; the profile supplies
large-document allocation evidence rather than a machine-dependent unit-test
memory threshold.

## Reproduce

Use the shared validation slot for each command. Substitute absolute paths
for the site, output and four sample documents:

```powershell
dotnet run -c Release --no-build --no-restore --project tools\AdoBye.EditorSmoke -- --profile <site> <output.json> <01.pdf> <03.pdf> <09.pdf> <20.pdf>
dotnet run -c Release --no-build --no-restore --project tools\AdoBye.EditorSmoke -- --profile-summary <output.json>
```

The summary-only command applies the same default failing budgets to saved
measurements, without rerunning the browser. Diagnostic reports can be
generated with the explicitly named report-only environment setting.

Release validation: the focused image/editor/ICC/JPEG/JPX selector passed
303 tests; the final solution build succeeded and the full solution test run
passed **1703/1703**, with no failures or skips. This adds seven deterministic
image cases to the accepted integration checkpoint's 1696 tests.
Fresh 207-artifact WASM publish, full Chromium, `--merge`, and `--page-image`
on sample 26 all passed. Their deliberately invalid/encrypted uploads and
recovery quota failures are expected negative cases, not unexpected browser
errors. The smoke checks retain local-only PDF traffic assertions.

## Remaining work

The under-250 ms open goal is still missed by the image and showcase samples.
Fresh raster/zoom work remains hundreds of milliseconds to multiple seconds;
this is not fixed by low heartbeat latency. Single-threaded raster work,
repeated image decoding, thumbnail work competing with edits, and uncached
page metadata remain candidates for the next measured slice. Speculative
neighbor rendering must not extend the worker queue ahead of interactive
commands. Recovery coalescing intentionally trades durability delay for fewer
full snapshots, and no "saved" status is shown before the write completes.

The separate dated library benchmark report retains corpus and noise caveats.
Regenerated samples are not byte-identical to the previous Python-authored
corpus, so historical sample timings cannot isolate library changes.
