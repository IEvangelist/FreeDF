# User-local WebAssembly AOT experiment: 2026-10-30

This follows the [first performance checkpoint](2026-10-30.md). It is **not
completion of editor responsiveness or PDF spec parity**. The initial comparison
used explicit `-Aot` publishing. Following validation, the Pages workflow now
selects AOT by default; no push or deployment was performed here.

## Toolchain and controls

The official SDK installer successfully installed the repository-pinned SDK
10.0.403 into a user-writable directory, followed by `wasm-tools` 10.0.14 without
elevation. The installed SDK/packs occupy 2,295,725,340 bytes (2.30 GB); the SDK
archive alone was 300,745,255 bytes. The first successful native publish took
approximately 4m43s. Installation duration was not captured reliably. The
machine-wide elevated installation was not retried.

AOT requires `PublishTrimmed=true`. The experiment roots the editor and four PDF
assemblies to preserve anonymous/reflection-based JSON payloads, while trimming
the framework. It retains globalization data, IL bodies, synchronous browser
cryptography limitations and the single-worker/no-threads architecture.
`WasmEnableSIMD=true` is explicit; current non-AOT .NET also enables SIMD and
uses the interpreter plus jiterpreter, not a purely interpreted runtime.

The matched control contains the same bounded PNG change as AOT. Three fresh
Chromium contexts per variant, Release, 1440 x 1000/device scale 1, same four
samples plus generated 12-page fixture, same existing end-to-end harness and
shared validation slot. Each command acquires/releases the slot independently.
These are unthrottled, uncompressed local-server timings, not public-network
latency or a production-tail distribution. Three-sample p95 is the maximum.

The [control CSV](2026-10-30-aot-control.csv) and [AOT CSV](2026-10-30-aot.csv)
retain all 535 metric groups, not just selected wins. Their corresponding
[control](2026-10-30-aot-control-budgets.json) and
[AOT](2026-10-30-aot-budgets.json) budget files retain failing goals.

Switching AOT/non-AOT in shared intermediates produced a broken control containing
trimmed assemblies with the stock interpreter. That failed startup is excluded
from comparison. A fresh `--artifacts-path` control booted successfully; use
separate intermediate **and** publish directories when changing compilation mode.
An initial profile also exposed a harness race: fitting a page was followed by
overlay input before the page became editable. The harness now waits for the
decoded/current image and non-inert view before sending input. No editor
readiness restriction was removed.

## Allocation and profiling

Browser PNG encoding now batches filter-0 rows into about 64 KiB instead of
allocating another full filtered page. A row wider than that uses one complete
row. The desktop path and thresholds are unchanged. Six deterministic tests
cover compressible/noisy/alpha pixels, partial batches, very wide rows and
allocation reduction. Compressed PNG bytes can differ; decoded pixels must not.

At 1985 x 2807 the earlier whole-page encoder allocated about 214.9 MB for the
render operation. The bounded encoder allocates **192,671,784 bytes** in both
matched compilation modes, avoiding about 22.2 MB. This is allocation volume,
**not a measurement of peak managed/native/JS working set**. Raster float buffers,
RGBA, PDF snapshots, JSON/base64 and browser image copies remain substantial;
AOT does not fix them.

`--raster-profile <site> <output-directory> <pdf>` attaches Chrome's CPU profiler
to the actual PDF worker, emits `.cpuprofile` plus stage/allocation/decoded-hash
measurements, and waits for recovery coalescing before sampling. Profiler
overhead means its durations are diagnostic, not benchmark comparisons.
The stripped runtime exposes mostly numeric native/JIT function names.
JPEG/JPX/Flate-specific managed hotspot attribution is therefore **not yet
established**; no speculative SIMD/unsafe decoder rewrite was made.

## Adoption, safety and hosted CI

The Pages workflow installs `wasm-tools` for the SDK pinned by `global.json`,
publishes with separate intermediates/output and runs all browser checks against
that output. Manual dispatch defaults to **validation only**, retains the site
and evidence as an artifact, and requires `deploy=true` explicitly to deploy.
Its `aot=false` input is the explicit non-AOT build fallback; it does not waive
regression gates. The workflow caches NuGet packages, not an installed SDK/packs
tree that could cross toolchain versions.

Expect several additional minutes for native compilation (4m43s locally),
plus the complete three-repeat browser profile and boot/merge/page-image checks.
Hosted-runner build time and network cold start have not been measured yet.

The JSON safety smoke round-trips state/fonts/text/objects/items, metadata, form
values and recovery through the actual worker. It applies a real whole-page
redaction, verifies find results disappear, reopens saved PDFs and checks the
intended metadata/form scrubbing, and exercises all browser export formats.
Full editor/recovery, encrypted-input rejection, keyboard/atomic merge,
boot/integrity faults and page-image continuity pass on the fresh isolated AOT
publish at `/csharp-pdf/`, without threads/shared-memory isolation.
The full Release suite passes **1709/1709**.

known groups, measured values and original goals, plus fixed-41-dpi pixel hashes.
CI prints/uploads **KNOWN MISSES (baseline open work)** and the full strict-goal miss table.

Timing CI uses ceilings of **2.5 times** each recorded AOT p50/p95, with a

## Follow-up measurement: binary uploads and next-page preview (2026-10-30)

The binary upload and preview changes were tested against a fresh `/csharp-pdf/`
AOT publish. The source and raw profile artifacts remain local to the session;
no Pages deployment or push was performed.

### Binary file upload

The 3,844,941-byte generated 12-page PDF previously spent 108-130 ms in worker
base64 encoding and JSON expansion. Blob uploads now pass a `Uint8Array` through
a small JS object to the `RequestBinary` JS export, which reads the byte array
directly into the existing .NET open path. The measured browser preparation
stage fell from 120.4 ms p50 to 6.7 ms p50 (18.3 ms p95); the managed dispatch
was 4.1 ms p50 and the combined worker open stage was 10.6 ms p50. This avoids
base64/JSON expansion but is not zero-copy: the runtime still materializes a
managed byte array. Non-Blob JSON request bodies and response encoding are
unchanged.

The large-document end-to-end open was already below budget after the upload
change (121.1/121.6 ms p50/p95) and measured 120.7/121.6 ms in the follow-up.
That difference is within run variation, not a separate speedup claim. All 15
matched first-page decoded pixel hashes remained equal.
